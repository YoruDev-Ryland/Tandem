# EmuSync Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the self-hosted EmuSync server. It stores save, state, config and vault versions, decides what
each device should receive, and exposes the device and web APIs, the live event stream, retention, off-server
backup, notifications, and a Docker image.

**Architecture:**
- **Shape:** one ASP.NET Core minimal-API app (`EmuSync.Server`), with feature folders that each hold
  endpoints and services, plus a small `EmuSync.Protocol` project holding the request/response records.
- **Storage:** metadata in EF Core (SQLite by default, PostgreSQL optional). File content in a per-user,
  content-addressed blob store on the data volume.
- **The server decides delivery.** Devices upload versions and report what they have installed. The server
  works out each device's pending deliveries: saves for installed games, config versions for the bundle the
  device follows, and vault placements. Path rewriting for configs happens on the server, so every client
  stays thin.

**Tech Stack:** .NET 10, ASP.NET Core minimal APIs, EF Core 10 (Sqlite + Npgsql), xUnit 2.9,
Microsoft.AspNetCore.Mvc.Testing, Microsoft.Extensions.TimeProvider.Testing, Testcontainers.PostgreSql,
Microsoft.AspNetCore.OpenApi, AWSSDK.S3 (backup target), Docker.

**Spec:** `docs/superpowers/specs/2026-11-19-emulator-save-config-sync-design.md`

**Out of this plan:** the web UI (Svelte, plan 4) and the Android app (plan 5). This plan serves a `wwwroot`
folder if one exists and exposes every API the web UI needs.

## Global Constraints

- A standalone project in `~/Development/EmuSync`, its own git repo. **No code, references, or
  submodules from PKForge.**
- `net10.0`, `Nullable` enable, `ImplicitUsings` enable, `TreatWarningsAsErrors` true, `LangVersion` latest
  (in `Directory.Build.props`).
- All API routes under `/v1/`. Every request carries the `EmuSync-Protocol: 1` header. A missing or other
  value returns 426 with error code `protocol_mismatch`, except for `/healthz`, `/v1/server-info` and static
  web files.
- Errors are JSON `{"code": "...", "message": "..."}`.
- Data lives in `DATA_DIR` (default `/data` in Docker, `data` otherwise). The Docker image runs on x64 and
  arm64.
- Environment settings (with ASP.NET form `EmuSync__X` also accepted):
  - `PUBLIC_URL`, `ALLOW_REGISTRATION` (default `false`; the first account can always register and becomes
    admin), `DATA_DIR`, `PUID`/`PGID` (default `1654`)
  - `DATABASE_PROVIDER` (`sqlite`|`postgres`), `DATABASE_CONNECTION`
  - `TRUST_FORWARDED_HEADERS` (default `false`), `SERVER_NAME` (default `EmuSync`, max 60 chars), `WEB_ROOT`
- Ordering never uses device clocks. Server times come from the injected `TimeProvider`.
- No device ever receives a version that would replace data the server doesn't already hold.
- Emulator module IDs are exactly `eden`, `retroarch`, `azahar`, `ppsspp`, `vita3k`, `dolphin`, `melonds`.
  Unknown IDs are rejected with 400 `unknown_emulator`.
- The protocol is platform-neutral: device `platform` is a free string (`android` now). Path placeholders
  are generic.

## Review Focus

1. **Two devices upload a change to the same save at the same moment from the same base** → exactly one
   becomes head and the other becomes a conflict. Never two heads, never a lost version. (Task 7)
2. **A device re-uploads a save identical to the current head** (e.g. after a reconnect) → `Unchanged`, no
   new version, no conflict. (Task 7)
3. **A device uploads a save for a game it no longer has installed** → accepted and stored, but not delivered
   to devices without that game. (Task 8)
4. **A config file with paths containing spaces, quotes or URL-encoded `content://` links, or with Windows
   line endings, and no path changes** → round-trips byte-identical through tokenize/expand. (Task 10)
5. **A multi-hundred-MB vault upload (Switch firmware) or a dropped connection mid-upload** → streamed to disk
   without buffering in memory, hash checked, no partial blob left behind. (Task 5)

## Shared vocabulary (used by every task)

- **ItemKind** (enum in Protocol): `Save`, `State`.
- **Save item identity:** `(UserId, EmulatorId, Kind, GameKey, Slot)`.
  - `GameKey` is a string chosen by the client module: a title ID, a game ID, or the ROM file name without
    extension prefixed with the platform, e.g. `gba/Golden Sun - The Lost Age`.
  - `Slot` is a string, `""` for the single save.
  - States also carry `Core` (string, `""` if not applicable), and for states **`Core` is part of
    identity**: `(…, Kind=State, GameKey, Slot, Core)`. For saves, `Core` is recorded on the version only
    (spec §13).
- **Manifest:** `IReadOnlyList<ManifestEntry>` where `ManifestEntry(string Path, string Hash, long Size)`.
  - `Path` is relative, uses `/`, and has no `..`.
  - `Hash` is lowercase hex SHA-256.
  - Manifests are sorted by `Path` (ordinal) before storing. The manifest hash is the SHA-256 of
    `path\0hash\0size\n` lines.
- **Version sequence:** each item has a monotonically increasing `long Seq` per item. Version IDs are `Guid`.
- **Conflict reason** (enum): `Concurrent`, `FirstSync`.
- **Delivery kinds** (enum): `Save`, `Config`, `Vault`.
- **Path tokens:** `{INTERNAL}` is primary storage, e.g. `/storage/emulated/0`. `{SD}` is the removable volume
  if present. `{EMU:<emulatorId>}` is that emulator's data root on that device.

### Task 7: Save and state versions, and conflicts (the core)

**Files:** Create `Saves/SaveService.cs`, `Saves/SaveEndpoints.cs`, `Saves/UserLocks.cs`. Test `SaveTests.cs`.

**Interfaces:**
- Consumes: `BlobService.RequireAllAsync`, `IDomainEvents`.
- Produces:
  - `POST /v1/saves/upload` `SaveUploadRequest(EmulatorId, ItemKind Kind, GameKey, Slot, Core, Guid? BaseVersionId, IReadOnlyList<ManifestEntry> Manifest, string? DisplayName)`
    → `SaveUploadResponse(SaveUploadStatus Status, Guid ItemId, Guid VersionId, Guid HeadVersionId)`, where
    `SaveUploadStatus` is `Accepted | Unchanged | Conflict`.
  - `SaveService.UploadAsync(userId, deviceId, SaveUploadRequest, ct)` runs under
    `UserLocks.Acquire(userId)`, a per-user `SemaphoreSlim`. On Postgres it also takes
    `SELECT … FOR UPDATE` on the item row. The rules, in order:
    1. Manifest invalid (absolute or `..` path, duplicate path, bad hash) → 400 `bad_manifest`. Missing blobs
       → 400 `missing_blobs`.
    2. Find or create the item. For `Kind=Save`, the item's `Core` is `""` and the request's `Core` goes on
       the version.
    3. If the item has a head whose `ManifestHash` equals the upload's → `Unchanged`. Set
       `DeviceItemState.KnownVersionId = head` for this device.
    4. No head → new version with `Seq=1`, becomes head → `Accepted`.
    5. `BaseVersionId == head` → new version, becomes head → `Accepted`.
    6. `BaseVersionId == null` and a head exists → new version **not** head, with
       `ConflictReason=FirstSync`. Set `OpenConflict=true` → `Conflict`.
    7. Otherwise (base is older or unknown) → new version **not** head, with `ConflictReason=Concurrent`.
       Set `OpenConflict=true` → `Conflict`.
    8. On `Accepted`/`Unchanged`, set this device's `DeviceItemState.KnownVersionId`. Raise
       `SaveHeadChanged(ItemId)` on `Accepted`, and `ConflictOpened(ItemId, VersionId, Reason)` on `Conflict`.
  - `POST /v1/conflicts/{itemId}/resolve` `ResolveConflictRequest(ResolveChoice Choice, Guid? KeepVersionId)`
    with `ResolveChoice` `KeepVersion | KeepBoth`:
    - `KeepVersion`: that version becomes head. The other conflict versions stay as history, with
      `ConflictReason` kept for display.
    - `KeepBoth`: `KeepVersionId` becomes head. Every other open conflict version gets
      `Variant = "<device name> <yyyy-MM-dd HH:mm>"` and `Pinned=true`.

    - **Encryption:**
      - Header: magic `ESBK1`, a 16-byte salt, and the 32-bit chunk size `1048576`.
      - Key: PBKDF2-HMAC-SHA256, 600 000 iterations, 32 bytes.
      - Body: AES-256-GCM per 1 MiB chunk. The nonce is a 4-byte zero prefix plus an 8-byte big-endian chunk
        counter, and each chunk is followed by its 16-byte tag.
      - The final chunk is marked by setting the counter's high bit.
  - `BackupService : BackgroundService`: runs daily at `HourUtc` (from `TimeProvider`), streams the archive to
    the target without staging it all in memory, keeps the newest `Keep` (default 7) backups at the target,
    and raises `BackupFinished(ok, error?)`.
  - `IBackupTarget`: `WriteAsync(name, Stream)`, `ListAsync()`, `DeleteAsync(name)`, `OpenReadAsync(name)`.
    Implemented by `FolderTarget` and `S3Target` (AWSSDK.S3, path-style when `Endpoint` is set).
  - CLI: `restore-backup <file> [--passphrase X]`, restoring into an **empty** data directory and database.
    It refuses if users exist.
- The UI must say that losing the passphrase means the backup can't be restored. This plan only provides the
  `PassphraseSet` flag, and plan 4 shows the warning.
